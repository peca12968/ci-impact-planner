# Message Parity｜上線前找出翻譯漏掉的訂單情境

顧客已選擇台中站自取，繁中通知卻顯示「請洽客服」。翻譯檔仍是有效 JSON，訊息也能正常顯示。原因是譯文漏掉 `pickup` 分支，格式化時套用了 `other`。這個 Node.js CLI 比對兩份 ICU 訊息目錄，報告有差異的訊息 ID、選擇條件與參數，供工程師和譯者一起修正。

## 重現草稿與修正版

在專案根目錄使用 Node.js 22 或 24。

```sh
npm ci
npm run demo
npm test
```

示範將同一筆資料分別套入草稿與修正版，用實際的 ICU 格式化器輸出六個顧客情境，並斷言修正版的文字符合預期。差異出現在以下三個情境。[英文來源](examples/en.json) · [繁中草稿](examples/zh-TW.draft.json) · [繁中修正版](examples/zh-TW.json)

| 情境 | 草稿的結果 | 修正後的結果 |
| --- | --- | --- |
| 退款 1234.5 元 | 金額直接插值，顯示 1234.5 | 以繁中地區格式顯示台幣金額，貨幣符號及小數位由 Intl 決定 |
| 台中站自取 | 請洽客服。 | 請至台中站取貨。 |
| 空購物車 | 購物車有 0 件商品。 | 購物車是空的。 |

## 在 CI 比對自己的目錄

```sh
node check.js en examples/en.json zh-TW examples/zh-TW.draft.json
node check.js en examples/en.json zh-TW examples/zh-TW.json
```

輸入是 UTF-8 JSON 物件，鍵為訊息 ID，值為 ICU 純文字訊息。第一條命令會寫出三項差異並回傳結束碼 `1`，第二條會回傳 `0`。檔案、語系、語法或支援範圍出錯時，會將原因寫至標準錯誤並回傳 `2`。報告中的 `branch` 是從外到內的選擇路徑，例如 `mode=pickup` 下的 `phase=ready`。

## 如何判定差異

- 使用 FormatJS 解析語法樹，按訊息 ID 及分支比對。參數可在同一分支調整順序或重複使用。若將門市名稱移到宅配分支，工具仍會指出原分支缺少門市名稱。
- `select` 的業務標籤、`plural` 的精確數值分支（例如 `=0`）、單複數或序數的選擇方式，以及 `offset` 都會納入比對。每個分支內也會檢查 `#` 的使用。
- 各語系的文法複數類別可以不同。以 Node.js 的 `Intl.PluralRules` 核對語系可用的類別，譯文使用來源也有的類別時會比對同名分支。譯文新增自己的文法類別時，會和來源的 `other` 比對。這讓英文的 `one` 可在繁中省略，同時保留業務上獨立的 `=0`。這項規則只檢查有寫出的文法分支，不判斷譯者是否應該為某語系增寫文案。[FormatJS 訊息語法](https://formatjs.github.io/docs/core-concepts/icu-syntax/)
- 數字參數會比對格式名稱或數字 skeleton 解析後的選項，涵蓋幣別與百分比。日期和時間保留參數角色，格式長短可由譯者決定。標點、語氣與一般文字的翻譯品質由人工審閱。

這個工具採用保留選擇器巢狀結構的翻譯契約。需要重新安排分支結構的翻譯會產生差異，適合一起審查。富文字標籤與同一層重複使用相同名稱的選擇器會回報輸入錯誤。

## 驗證

測試以兩層業務條件建立六條路徑，每條路徑有一個專屬參數。窮舉 64 種替換參數的組合，每種分別用六組資料執行格式化，共 384 次。每組靜態檢查指出的問題路徑，都與實際格式化失敗的路徑集合一致。另測試語系特有複數、貨幣格式、巢狀精確數值分支與 CLI 結束碼。[測試程式](test/parity.test.js) · [實際格式化示範](demo.js)

**履歷用語**　以 Node.js 與 ICU 語法樹實作多語系訊息檢查工具，找出分支遺漏、參數移位與金額格式變更，並用 384 次格式化執行驗證巢狀分支診斷結果。

本專案使用 AI 輔助開發，訊息與訂單情境均為合成範例。
